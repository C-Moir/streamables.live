Building V1.5 for $0 While Waiting for Budget

By Cameron J. Moir  ·  Streamables.live
//

The wrong move when you’re solo and unfunded and need a feature that costs API budget you don’t have: wait until you have the budget, then build the whole feature in one block.

The right move: build everything around the paid API for $0 right now, so the moment budget arrives the feature ships in a fraction of the time it would otherwise take.

This article is a case study in that pattern. ClipTips’ V1.5 video lipsync needs a Sieve API account ($20 free credit, then per-minute billing) that I don’t want to commit a card to until revenue exists. Without budget, I had three options:

  • Wait until budget arrives, then start the V1.5 build (3-4 weeks of work ahead of me).
  • Skip V1.5 entirely, ship audio-only forever, lose the marketing flagship feature.
  • Build everything around V1.5 for $0, leaving only the actual Sieve integration call gated behind the budget. ~Half a day of finishing work when budget arrives.

I picked option three. Here’s exactly what that looked like.

The shape of "build the surround"

The strategic insight: a feature is rarely just "the API call." Around any given paid API, there’s a galaxy of free work that has to happen anyway. Database schemas, storage buckets, UI components, server routes, telemetry, fallback paths, onboarding flows. All of it can be built before you ever spend a cent on the API itself.

For ClipTips V1.5 lipsync, the surround is:

  • A provider abstraction layer (so the Sieve integration can swap to fal.ai or Modal-self-hosted later without UI changes)
  • A face baseline storage system (Supabase Storage bucket, voice_profiles table extension, upload endpoint, recorder UI component)
  • A per-utterance recording pipeline (data flywheel that captures translated audio + metadata for replay + training)
  • The lipsync video panel UI inside the production session room (renders the synced output when present, falls back gracefully when not)
  • Cost accounting hooks (track Sieve minutes once they start arriving)
  • Feature flag wiring (so flipping V1.5 on is one env var change)

None of that needs Sieve. All of it costs $0 to build. All of it has to exist before V1.5 can ship anyway.

What I shipped in one push (Workstreams A, B, C)

The free-tier prep plan has three independent workstreams. Each ships value on its own; together they pre-build ~70% of V1.5.

Workstream A - Voice recording infrastructure. New Postgres table live_interpreter_utterances, private Supabase Storage bucket live-interpreter-audio, POST endpoint /api/live-interpreter/utterance/save, server-side wiring inside LiveInterpreterRoom.tsx that captures the played PCM bytes after each utterance + posts them back with metadata. Fire-and-forget, off the critical latency path. Why first: data flywheel. Every audio-only session that ships without recording is permanently lost training data. Compounds daily.

Workstream B - Face baseline storage. New column voice_profiles.sample_video_url, private Supabase bucket face-baselines, POST endpoint /api/live-interpreter/face-baseline, new React component FaceBaselineRecorder (10-15 second video capture via MediaRecorder), wired into /settings for signed-in users. The recorder reuses the same one-time capture flow as voice cloning - one signup step, two derived artefacts.

Workstream C - Lipsync UI scaffolding. New component LipsyncVideo.tsx with three render states (waiting / streaming / unavailable), wired into LiveInterpreterRoom as the primary video panel above the live captions, plus a primary/inset toggle button. All inert until the streaming-lipsync provider returns a stream URL. When V1.5 ships, the UI is already there.

Total: 12 commits across the day, ~1,100 lines of new code, two Supabase migrations, three new API endpoints, two new components, one provider abstraction. Zero in API spend.

The half-day finish

When the Sieve API budget arrives, V1.5 ships with these tasks:

  • Provision Sieve account, generate API key, paste into .env.local + Vercel env (~10 minutes)
  • Curl-test the Sieve MuseTalk endpoint with a sample face video + audio clip to verify the API contract matches their docs (~30 minutes - the only real unknown)
  • Replace the throw-stub in src/lib/streaming-lipsync/sieve-provider.ts with the real upload + poll + return flow (~2-3 hours)
  • Wire /api/live-interpreter/lipsync server route to call the provider and stream the synced video back (~1-2 hours)
  • Connect the LipsyncVideo component’s streamUrl prop to the lipsync API output via MediaSource (~1 hour)
  • Flip NEXT_PUBLIC_LIVE_INTERPRETER_LIPSYNC_ENABLED=true on Vercel

Half a day, maybe a full day with debugging. Compared to the 3-4 weeks the work would take starting from scratch.

The compression isn’t magic. It’s the inverse of the "tech debt" framing. Most "tech debt" articles talk about the cost of postponing cleanup. The flipside, less written about: front-loading scaffolding for features you can’t afford yet creates option value. The infrastructure I built today exists in the codebase whether V1.5 ever ships or not. If lipsync turns out to be a dead end (API costs spike, quality issues, market doesn’t care), the data flywheel and face baseline storage are still useful for replay, audit, training data, future features. None of it is wasted.

Why this works for solo + unfunded

Two reasons:

Time has a different shape when you’re solo. A funded startup might say "we’ll wait to start V1.5 because we have other priorities." A solo founder doesn’t have other priorities competing for the same hour - if I’m sitting at the keyboard at 11pm and the V1.5 build is gated on budget, I can either build the surround for $0 or do nothing. Building wins every time.

The compounding effect is bigger when you have less. A funded team can throw a sprint at V1.5 the moment they decide to. A solo founder benefits more from front-loaded work because the "decide to ship V1.5" moment becomes "press the deploy button." That gap matters when you’re trying to ship features in time-windows between day-job hours.

The danger is over-engineering. Building infrastructure for features you’ll never ship is just stash-buying. The discipline is: build only the surround for features you’re definitely shipping. The V1.5 lipsync isn’t a maybe - it’s the next major release, gated only on funding. Pre-building it is rational.

Pre-building speculative features ("we might add comments someday so let’s build a comments service now") is irrational. The difference is whether the feature has a clear path to shipping or just lives in your head as a "wouldn’t it be cool if."

Reusable pattern

If you’re solo and unfunded and there’s a paid-API feature you want to ship, the recipe is:

  • Map the surround. Every database row, storage bucket, API endpoint, UI component, telemetry hook, feature flag.
  • Sort by dependency. What can ship without the paid API? Build that first.
  • Mock the paid API call as a throw-stub or no-op, sitting behind a clean interface.
  • Wire everything else to that interface as if the API was real.
  • Test the surround against the stubs. UI states, fallback paths, error handling.
  • When budget arrives, replace the stub with the real call. Everything else already works.

For V1.5 lipsync, "everything else" was about 70% of the total feature work. The Sieve integration itself - the part that actually costs money - is the smallest piece.

That ratio holds for most paid-API features I’ve built. The headline cost (the API call) is rarely more than 20-30% of the actual implementation. Front-load the rest.
