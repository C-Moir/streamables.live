The Provider Abstraction Pattern

By Cameron J. Moir  ·  Streamables.live
//

Every external dependency in ClipTips sits behind a small provider abstraction. Seven of them: streaming transcription, streaming TTS, streaming lipsync, voice cloning, text translation, video calls, transactional email. Each provider has the same shape - an interface, one or more implementations, a factory that picks one based on env vars.

This is one of the highest-leverage patterns I’ve used on a solo build. It looks like over-engineering until the day a provider goes down, raises prices, or gets bought by a competitor. Then it looks like the only thing keeping the platform alive.

This article walks through the pattern with the actual code from ClipTips, why it matters more for solo founders than funded teams, and where the line between "useful abstraction" and "premature complexity" actually sits.

The shape

Every abstraction follows the same three-file structure:

provider.ts - the interface. Defines exactly what callers can ask for and what they get back. No implementation logic. Type-only.

elevenlabs-provider.ts (and siblings) - the implementations. One file per provider. Each implements the interface against a specific vendor’s API. Errors throw, options get validated, the response gets shaped to match the interface.

index.ts - the factory. Reads an env var (e.g. STREAMING_TTS_PROVIDER) and returns the matching implementation. Default sensibly. Throw on unknown values.

Concrete example - streaming TTS:

  • src/lib/streaming-tts/provider.ts defines StreamingTtsProvider with one method: synthesiseStream(opts) => Promise<StreamingTtsResult>.
  • src/lib/streaming-tts/elevenlabs-provider.ts implements it via the ElevenLabs streaming HTTP endpoint.
  • src/lib/streaming-tts/cartesia-provider.ts is a stub for the fallback case.
  • src/lib/streaming-tts/index.ts exports getStreamingTtsProvider() which reads STREAMING_TTS_PROVIDER env (default: elevenlabs) and returns the right one.

Caller code:

const tts = getStreamingTtsProvider()
const result = await tts.synthesiseStream({
  text:     translatedText,
  language: targetLang,
  voiceId:  speakerVoiceId,
  quality:  ‘fast’,
})

The caller has no idea which vendor answered. It can’t tell. That’s the point.

The seven abstractions in ClipTips

  • streaming-transcription - Deepgram (real), AssemblyAI (stub). Switching is one env var.
  • streaming-tts - ElevenLabs (real), Cartesia (stub). Switch via env.
  • streaming-lipsync - Sieve (stub waiting on budget), fal.ai (stub). Will swap when budget arrives.
  • voice-clone - ElevenLabs (real), Cartesia (stub). Different from streaming-tts because cloning is a one-shot operation, not a real-time stream.
  • text-translation - DeepL (real), OpenAI (real), OpenRouter (real). Three implementations because translation quality varies by language pair and OpenRouter unlocks Claude / Llama via one API.
  • video-call - Daily.co (real), Jitsi (real). Originally Jitsi-only; Daily got added later when room creation patterns matured. Switching is per-session via the video_provider column on the sessions table.
  • mailer - Resend (real), Postmark (real), console (dev fallback). Three because transactional email reliability is one of those things you don’t want to discover is broken at 11pm.

Each one is the same three-file pattern. Total LOC across all seven: maybe ~1,500 lines. Maintenance burden: ~zero, because the interfaces are stable and implementations rarely change.

Why this matters more on a solo build

Funded teams can absorb a vendor outage. They have engineers on call, multi-region failover already wired into their infrastructure, time to negotiate with sales when prices change. A solo founder doesn’t.

The realistic threats to a vendor dependency on a solo build:

Outage. Provider goes down for hours. Without abstraction: platform broken. With abstraction: env var change + redeploy = swap to backup provider. ~5 minutes.

Price hike. ElevenLabs doubled their character pricing in 2024 with 60 days notice. Without abstraction: emergency code rewrite. With abstraction: switch to Cartesia or Resemble while you negotiate.

An acquisition. Provider gets bought, terms change, or the new owner deprecates the API. HeyGen-Captions style situations. Without abstraction: stranded. With abstraction: same swap path.

A hard rate-limit. Volume surges on a launch day, you hit the provider’s tier ceiling, requests start failing. Without abstraction: outage. With abstraction: shed load to the backup provider mid-flight.

None of these are hypothetical. All four happen to working products every year. The cost of the abstraction is the time to write 30-50 lines of interface + factory code per dependency. The cost of NOT having it shows up at exactly the wrong moment.

The interface design rules I follow

Five rules that make abstractions actually portable across vendors:

1. Optional fields are your friend. Different providers expose different parameters. ElevenLabs has voice settings (stability, similarity_boost). Cartesia doesn’t. The interface accepts both vendors’ full feature set as optional fields; each implementation uses what its vendor supports and ignores the rest.

2. Return concrete types, not vendor enums. ElevenLabs returns audio in audio/mpeg or audio/L16. Cartesia returns audio/wav. The interface returns { audioStream, sampleRate, encoding: ‘pcm_s16le’ | ‘mp3’ }. Each implementation translates from vendor format to this canonical shape. Callers never see vendor-specific values.

3. Errors throw with provider context. When a call fails, the error message includes which provider answered. "ElevenLabs streaming TTS failed (402): paid plan required" is more debuggable than "TTS failed." Crucial when you’re solo and the next debugging session is in three days.

4. Provider names go through the type system. type StreamingTtsProviderName = ‘elevenlabs’ | ‘cartesia’ instead of string. The factory throws on unknown names at startup, not on first request. Catches typos in env vars before they hit production.

5. Keep the interface narrow. Don’t expose every vendor capability. Expose what callers actually need. synthesiseStream(opts) is one method, not fifteen. If a caller wants something the interface doesn’t expose, that’s a signal to widen the interface deliberately, not bypass it.

When abstraction becomes over-engineering

Three cases where the pattern doesn’t pay back:

Single-vendor categories. Stripe for payments. There isn’t a good reason to abstract Stripe behind PaymentProvider interface unless you’re preparing for a Stripe-PayPal multi-provider strategy (most products aren’t). Skip the abstraction; let Stripe SDK calls live in your code.

Internal services you control. Don’t abstract your own database access behind DatabaseProvider interface unless you’re actively migrating between Postgres and MySQL. The abstraction adds noise without protection because you control both ends.

Free-tier-only dependencies. Cloudflare for DNS, GitHub for hosting code. These don’t need abstraction because the cost of switching is negligible (DNS records can move in an hour) and the lock-in is minimal.

The rule of thumb: abstract if the dependency is a paid third-party with realistic substitutes that have meaningfully different APIs. If those three conditions all hold, write the interface. If any one is missing, don’t.

The migration test

The proof an abstraction works isn’t how clean it looks at write-time. It’s how easily you can swap implementations in panic mode.

Two real migrations from ClipTips:

Deepgram nova-3 to Flux. One-line change in deepgram-provider.ts: model: ‘nova-3’ → model: ‘flux’. No caller-side changes. Shipped in 30 minutes including testing + commit.

ElevenLabs Multilingual v2 to Flash v2.5. One-line change in elevenlabs-provider.ts. No caller-side changes. Plus a quality field exposed at the interface for callers who want explicit control. Shipped in an hour.

If either of those migrations had needed me to chase calls across 20+ files, change request shapes, update mocks, the latency optimisation we shipped this week would have taken days instead of hours. The interface paid back in a single afternoon.

What you can copy

If you’re building anything with paid third-party APIs and you might ever need to swap them:

  • Define the interface in a separate file from any implementation. Type-only.
  • Implement against one vendor first. Don’t pre-implement the second one - stub it with throws so the import is resolved but a real call hits a clear error.
  • Wire the factory + env-var selection from day one. Default to your real provider; the stub is just for type-safety and future replacement.
  • Run the dev path through the abstraction. Don’t bypass it for "easier debugging." Debugging through the interface is the actual product behaviour.
  • Document the interface with comments inline. Not separate docs. The docstring above each method should explain what it does and what providers can / can’t do.

Total dev cost on a single abstraction: 1-2 hours. Total payback over a project lifetime: at least 10x that, usually more.
