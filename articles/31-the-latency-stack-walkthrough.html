The Latency Stack Walkthrough

By Cameron J. Moir  ·  Streamables.live
//

This is a tutorial. If you’re building real-time AI conversation pipelines and you keep hitting "it works but it feels laggy," read on. The five-stage breakdown below is exactly what ClipTips runs in production, with the actual measurements and the optimisations that mattered.

End-to-end latency on the live interpreter pipeline sits at ~250-400ms today. Speaker stops talking; listener hears their cloned voice in another language ~300ms later. That’s "feels truly conversational" territory. A year ago the same pipeline ran at ~1,500ms and felt like a delayed Skype call.

The pipeline has five sequential stages. Any one of them slow and the whole thing breaks. Compress all five and you cross the threshold from "AI translation tool" to "actual cross-language conversation."

Stage 1: Mic to final transcript (~300-400ms)

Audio frames stream in continuously from the speaker’s microphone. The streaming transcription provider buffers them, runs realtime ASR, and emits two flavours of result:

  • Interim transcripts - partial guesses that keep changing as more audio arrives. "How do I make..." becomes "How do I make pasta..." becomes "How do I make pasta carbonara..." Each interim is just a snapshot of the model’s current best guess.
  • Final transcripts - emitted when the provider decides the speaker has finished an utterance. Triggered by silence detection (the "endpointing" parameter) or end-of-stream signals. Once final, the text is locked.

You can’t translate an interim. The text changes mid-translation and you’d call the LLM five times for one sentence, with five different outputs feeding into TTS, all of them slightly wrong. So the pipeline waits for finals.

The default endpointing on most providers is 300ms - the silence threshold before declaring an utterance final. Drop it to 150-200ms and you trade some false-positives on natural pauses for ~100-150ms of saved latency. Worth it for conversational use cases. Painful for legal transcription where you can’t cut someone off mid-thought.

Model choice matters too. Deepgram has nova-3 (their flagship), nova-2 (older, slightly cheaper), Flux (purpose-built for two-party realtime turn-taking). Switching from nova-3 to Flux on ClipTips saved another ~150ms - same $0.0077/min PAYG price, faster is_final emission. Different providers have different tradeoffs; the principle is "pick the model trained on your problem shape."

Best achievable on Stage 1 with current commercial providers: ~300-400ms. Below that you’re looking at on-device transcription (Whisper.cpp via WebAssembly) or self-hosted Riva, both with their own infrastructure costs.

Stage 2: Translation API (~150-400ms)

Final transcript arrives. Now translate it.

The naive path: HTTP POST to OpenRouter / Anthropic / OpenAI with the source utterance, wait for the full translated string back. ~200-400ms depending on model + utterance length.

The faster path: streaming token responses. The first token arrives in ~150ms; each subsequent token in ~50-80ms. You can pipe tokens directly into the next stage (TTS) instead of waiting for the full sentence to arrive. The "first audio byte at the listener" can start happening before the LLM has finished translating the rest of the sentence.

Pipelining trick that matters here: most TTS providers have a streaming endpoint that accepts incremental text chunks. ElevenLabs, OpenAI TTS, Cartesia all support this. So the translation tokens arrive in order, get streamed into the TTS endpoint, and audio synthesis starts on the first token instead of the last one.

ClipTips today doesn’t do token-streaming yet - the production path waits for the full translated string before kicking off TTS. That’s ~200-300ms of latency on the table. Phase B optimisation, queued for the next ship cycle. The architecture supports it; it’s a refactor of /api/live-interpreter/translate-speak not new infrastructure.

Best achievable: ~150ms first translated token. Realistic when streaming + a fast model (Claude Haiku 4.5, GPT-4o-mini, Llama 3 70B-Instruct).

Stage 3: Streaming TTS first byte (~75-500ms)

Biggest single optimisation this week. Switching ElevenLabs from eleven_multilingual_v2 to eleven_flash_v2_5 dropped TTS first-byte latency from ~400ms to ~75ms. That’s a 5x reduction on a single stage.

Both models support voice cloning (Instant Voice Clone and Professional Voice Clone). The Flash model is smaller and faster; Multilingual v2 has slightly richer prosody and a marginally more faithful voice clone. For live conversation where the listener priority is comprehension over exact tonal match, Flash wins. For recorded broadcasts where prosody matters more than first-byte speed, v2 wins.

I exposed this as a quality: ‘fast’ | ‘high’ field on the streaming-tts provider interface so callers can pick per-request. The live interpreter sessions default to ‘fast’; future flows that need higher fidelity (recorded post-session dub, premium playback) opt into ‘high’ explicitly.

One-line change in src/lib/streaming-tts/elevenlabs-provider.ts:

  • model_id: ‘eleven_multilingual_v2’ → model_id: ‘eleven_flash_v2_5’

~325ms saved per utterance, no behavioural change for callers.

Other providers worth knowing: Cartesia’s Sonic ~80ms first byte. OpenAI TTS HD ~600ms. PlayHT Turbo ~150ms. Pick the one with the cloning fidelity you need at the lowest first-byte you can tolerate.

Stage 4: Video frame buffering (V1.5 territory, ~200-500ms)

This stage doesn’t exist on the audio-only pipeline. It enters when V1.5 ships - lipsync of the speaker’s face video to the translated audio.

The problem: lipsync needs both the audio chunk AND a few seconds of the speaker’s face video. While Stages 1-3 are running, the speaker’s camera is still capturing live frames but we don’t know yet what audio those frames will be lipsynced to (the translation hasn’t finished yet). So we have to buffer frames.

Naive buffering: capture frames during the whole utterance + wait for audio + run lipsync on the buffered frames. Adds ~500ms.

Optimised buffering: pre-buffer a "neutral face" cache (captured once at session start, reused as the lipsync source) so we don’t need fresh capture for every utterance. Plus chunked streaming inference - process 200ms of audio + 5 frames at a time, output frames stream out as they’re ready. Plus predictive frame extrapolation for the periods between audio arrivals.

Best achievable: ~200-300ms.

Stage 5: Lipsync inference + return (V1.5, ~150-500ms)

Send the buffered face frames + audio chunk to the lipsync model, get back synced output frames. ClipTips’ V1.5 plan uses MuseTalk (Tencent 2024, MIT-licensed) hosted on Sieve at $0.14/min generated video.

Latency budget: ~200-500ms via Sieve hosted, ~150-200ms self-hosted on Modal A10 in same region as the Daily call. Self-hosting saves ~100ms by removing the network round-trip but adds significant ML engineering work to optimise the pre/post-processing pipeline (face detection, crop alignment, mouth masking, output stitching). MuseTalk’s core inference is fast; the surrounding pipeline is the actual bottleneck.

For ClipTips, Sieve hosted is the day-1 path. Self-hosting becomes a Phase 7 cost-optimisation pass once volume justifies the dev investment.

The compressed total

Add up the optimised numbers:

  • Stage 1 (transcript): ~350ms
  • Stage 2 (translation): ~150ms first token, full sentence ~250ms
  • Stage 3 (TTS first byte): ~100ms
  • Stages 4+5 (V1.5 lipsync): ~400ms total

Audio-only total (Stages 1-3): ~250-400ms. ClipTips today.

Audio + V1.5 total (Stages 1-5): ~1,000-1,200ms. ClipTips when V1.5 ships.

The first number feels conversational. The second feels like talking through a bad satellite link, but every alternative (avatars, captions-only, post-session dubbing) trades a different kind of UX cost. ~1s with synced video beats ~300ms with mismatched lips for most users.

The pipeline shape that matters most

Above all the per-stage optimisations: parallelism is more important than per-stage speed. The biggest mistake when building real-time AI pipelines is running stages sequentially when they could overlap.

Concrete examples in the live interpreter pipeline:

  • Stage 2 streams tokens to Stage 3 instead of finishing then handing off (buys ~250ms).
  • Stage 4 frame-buffering happens during Stages 1-3 instead of waiting for them (buys ~300ms).
  • Captions render on the listener’s screen at the end of Stage 2 - they don’t wait for audio playback (buys perceived latency: user has something to read while audio catches up).

The "naive total" of 2,600ms compresses to ~1,000ms not because any single stage got faster, but because three stages now run in parallel where they used to run in series. That’s the difference between a pipeline that feels broken and one that feels native.

What you can copy

If you’re building anything real-time-AI-shaped, the recipe is:

  • Pick a streaming-capable provider for every stage. Don’t ever use batch endpoints in a realtime pipeline.
  • Default to the fastest model your quality bar allows. Flash > v2 if comprehension > tonal exactness.
  • Tune endpointing thresholds aggressively. 150-200ms is fine for conversation; 300ms+ is for transcription accuracy.
  • Pipeline-overlap stages wherever the data dependencies allow. Token-stream from translation directly into TTS. Pre-buffer video while audio is processing.
  • Render captions / partial UI updates BEFORE the full audio arrives. Perceived latency is what the user feels.
  • Provider abstractions matter. When a faster model ships next month, you want a one-line switch, not a rewrite.
